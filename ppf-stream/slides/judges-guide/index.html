ICPC PROBLEM DATA · JUDGES’ GUIDE

Changing generated
test data, and shipping it

Part 1, for judges: edit a large case and let the commit hook turn it into a patch. Part 2, for the chief judge: choose, per problem, how it goes to the contest system.

November 2026 · a regional contest’s problem repository

This deck is the how-to that goes with the decision deck. Large secret files are no longer stored; each is a one-line pin that the problem’s own generator reproduces. Judges still edit data by hand; the tooling turns those edits into small patches. The chief judge decides per problem whether the contest system receives the full data or generates it on the judgehost.

PART 1 · JUDGES · WHAT CHANGED

A large case is now one line: a pin

data/secret/<case>.in:
#ppf-stream regen secret/<case>.in sha256=f8bce43d… size=2577788

The generator makes it

generators/regen.sh runs the problem’s own generator. The pin says exactly which bytes it must produce.

Hand edits ride along

An edit is kept as generators/patches/<case>.patch, applied after the generator, before the pin is checked.

CI checks every byte

verifyproblem runs on the restored data. A wrong byte stops the build; it never judges against wrong data.

41 problems, 128 large files. Small cases (under 2 MiB) stay ordinary files.

Judges used to see multi-megabyte files, stored in Git LFS. Now each of those files is a pin: a sha256 and a size. The data comes back whenever it is needed, from the generator, plus any patch, and is checked against the pin. Nothing about small hand-written cases changes.

PART 1 · JUDGES · ONCE PER CLONE

Turn on the commit hook

git config core.hooksPath tools/hooks

What it does

Before each commit, it looks for pinned cases you staged as data. Unchanged ones go back to their pin. Edited ones become a patch plus a new pin.

What you need

Python 3 and the generator’s toolchain (a C++ compiler for some problems). The same things CI uses.

Without the hook, run python3 tools/ppf_stream/sync.py problems/drafts/<problem> before committing. It does the same, for one problem.

One command, once per clone. The hook lives in the repository, so everyone gets the same version. If someone forgets it, nothing is lost: the pull-request check refuses pinned data committed as data and says what to run.

PART 1 · JUDGES · THE EVERYDAY CASE

Change a case in three steps

1 · OPEN

python3 tools/ppf_stream/expand.py problems/drafts/<problem> secret/<case>.in

2 · EDIT

$EDITOR problems/drafts/<problem>/data/secret/<case>.in

3 · COMMIT

git add problems/drafts/<problem>
git commit -m "<problem>: add a boundary edge"

sync: secret/<case>.in: 194-byte patch; pinned to the edited bytes (2,577,791 bytes)

The commit holds a 194-byte patch and a one-line pin, not 2.6 MB.

Step 1 writes the full generated file for that one case, with any earlier patch already applied. Edit it any way you like: add a line, remove a line, change a value. Then stage the problem directory and commit. The hook prints one line per file it handled. Stage the problem directory rather than using git commit -a: two .cpp files under problems/ready show as modified in every checkout and would be swept in.

PART 1 · JUDGES · WHAT THE HOOK DECIDES

Each staged pinned case gets one of four outcomes

You staged…The hook…
Data identical to its pinWrites the pin back. Opening every case and committing changes nothing.
Data you editedDiffs it against the generator’s own output, writes the patch, re-pins to your bytes
Data edited back to the generator’s bytesRemoves the old patch and re-pins
A deleted caseRemoves its patch, if it had one

144–194 B

patch per edit in testing, against 2.5–5.5 MB cases

0

bytes of data enter Git history; the patch is checked to reproduce your file before it is written

A patch is always measured against the generator’s raw output, never against an earlier patch, so editing the same case twice leaves one patch, not two. If the hook finds that nothing remains to commit, because every staged case matched its pin, it stops the commit instead of leaving an empty one.

PART 1 · JUDGES · OTHER CHANGES

Adding, removing, and changing the generator

To…Do this
Add a small caseAdd the .in and .ans as usual: under 2 MiB, they are ordinary files
Add a large caseMake the generator write it, then sync.py <problem> --repin secret/<new>.in
Remove a casegit rm the pin (and its .ans) and commit; the hook drops its patch
Change the generatorsync.py <problem> --repin re-pins every case that changed
Look at all the dataexpand.py <problem>; committing puts untouched cases back as pins

Commands are under tools/ppf_stream/, run with python3. The full guide is tools/ppf_stream/EDITING.md.

Most changes are the everyday edit on the previous slides. A generator change is the one that needs a deliberate step: re-pinning says “the new output is correct”. Existing patches are applied on top during re-pinning; one that no longer fits stops the command and names the case.

PART 1 · JUDGES · OPTION 3

No working generator? Shim it with a tar.xz

python3 tools/ppf_stream/archive.py problems/drafts/<problem> secret/<case>.in
# generator crashes: expand, then archive every large case and stop running it
python3 tools/ppf_stream/archive.py problems/drafts/<problem> --replace

What it does

Adds the cases to generators/data.tar.xz and pins them. regen.sh unpacks the archive after the generator, so archived cases win.

What stays the same

Opening, editing, the hook, patches, and both ways of deploying. problem A and problem B work this way today.

The cost

Real data in Git, about a third of its size, re-committed on every change. Split into parts under 2 MiB automatically.

When the generator is fixed: put it back in regen.sh, delete the archive, and run sync.py <problem> --repin.

Use option 3 for a hand-made large case, a generator that crashes, or one whose output has drifted from the data the problem was tested with. Name the cases to archive, or let archive.py take every data file of 2 MiB or more. The archive is reproducible byte for byte, so rebuilding it from the same files changes nothing in Git.

PART 1 · JUDGES · WHEN SOMETHING SAYS NO

Four messages and what they mean

MessageWhat to do
CI: pinned test data committed as dataThe hook was off. Run sync.py on the problem, commit the pin and patch.
A patch does not apply (after a generator change)The generator moved under your edit. Open the case, redo the edit, commit.
CI: sha256 mismatch for a caseThe generator no longer makes the pinned bytes. Fix it, or re-pin if the new output is right.
sync: nothing left to commitEvery staged case matched its pin. Nothing was lost; the commit was stopped on purpose.

A generator that can’t be fixed in time: use option 3, the tar.xz shim on the previous slide.

Every failure is loud and names a file. The one that matters most is the sha256 mismatch: it means the data a contestant would be judged on is not the data the problem was tested with, so the build stops rather than guessing.

PART 2 · CHIEF JUDGE · THE CHOICE

On an unchanged contest system, only option 2 keeps the data out of it

Option 2 · generate on the judgehost

The problem is uploaded interactive in name only. Its validator regenerates the data on first use, checks every pin, and caches it. The contest system stores pins and generators.

Fallback · upload expanded

The package is expanded before upload and is an ordinary problem. The contest system stores the full data, as it does today. Use it where option 2 can’t be.

Generating at import (option 1 inside the contest system) needs PC², DOMjudge or Kattis to add an import step, so it is not a choice for this contest.

The chief judge picks, per problem, how it reaches the contest system. Without any change to PC², DOMjudge or Kattis there are two ways: option 2, the only one that generates on the contest side, and uploading the expanded package, which works everywhere but stores the full data. The next slides say which problems can use option 2 and how to run it safely.

PART 2 · CHIEF JUDGE · PER PROBLEM

Four questions decide each problem

QuestionIf yesIf no
Does it have its own output validator, or is it already interactive?Upload expandedNext question
Does an accepted solution read input to end of file?Upload expandedNext question
Do the judgehosts keep the validator’s cache between runs?Next questionUpload expanded
Can every judgehost be warmed before the contest?Option 2Upload expanded

package.py checks the first question and warns on the second. The last two are about your contest system and judgehosts: confirm them in the test contest.

The first question is mechanical: option 2 replaces the output validator, so a problem with its own cannot use it yet. The second matters because problemtools’ interactive harness keeps a submission’s input open until the validator exits; a program that reads to end of file waits forever and times out. Many Python solutions read that way. The third and fourth are about the judgehosts: if the cache is thrown away after every run, every submission waits for generation.

PART 2 · CHIEF JUDGE · BUILDING THE UPLOAD

One command per problem, either way

python3 tools/ppf_stream/package.py problems/drafts/<problem> --option 2
python3 tools/ppf_stream/package.py problems/drafts/problem C --option 1

--option 2

Builds the interactive package, regenerates once and checks every pin, then writes <problem>-option2.zip. Refuses a problem with its own validator; warns on end-of-file readers.

--option 1

Expands every pin, checks it, and writes an ordinary package as problem C-option1.zip, ready for any contest system.

Never touches the repository: it builds in a scratch copy. Files sit at the zip root with problem.yaml on top.

package.py is the only command the chief judge needs. It works from the option1 branch, where every problem is pinned. Option 2 also warms this machine’s cache as a side effect of checking the pins, which is not the judgehosts’ cache: those are warmed by the test contest. Upload the zips the usual way for PC², DOMjudge or Kattis.

PART 2 · CHIEF JUDGE · BEFORE THE CONTEST

Warm every judgehost, then run twice

1 · TEST CONTEST

Judge every accepted solution

The first run on each judgehost regenerates and checks the pins. Its verdicts don’t count: a time limit hit while generating is expected.

2 · SECOND RUN

Judge them again

Now the cache is warm. Every accepted solution must pass. A timeout here is the end-of-file problem: upload that one expanded.

3 · CONTEST

Don’t clear the cache

The cache is in the temp directory, or PPF_STREAM_CACHE if set. A judgehost restarted or added later must be warmed again.

Cold generation took a median of 1 s per problem, 80 s for the slowest (problem G), about 3 minutes for all 40 on one laptop.

This is the run-twice policy from the decision deck, applied to a contest. The first pass exists to fill the cache on every judgehost, so no contestant’s submission ever waits on a generator. The second pass is the real check, and it also catches any solution the end-of-file warning missed. Keep both passes on the schedule for the test contest, and repeat them for any judgehost that joins late.
