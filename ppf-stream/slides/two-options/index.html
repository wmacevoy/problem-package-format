ICPC PROBLEM DATA · PROPOSAL FOR DECISION

Large test data:
generate it, don’t store it

Two ways to drop Git LFS for generated secret data, plus option 3, a tar.xz shim where a generator is broken or missing, tested on the 41 problems of a regional contest’s repository that use it today.

November 2026 · prepared for the problem-repository maintainers and the Kattis team

This deck compares two ways to stop storing large, generated test data. Option 1 regenerates it at build time; option 2 regenerates it at judge time behind an interactive validator. Everything here was measured on real contest problems on private branches; nothing has been merged.

WARNING

ICPC will likely not support Git LFS in the future

LFS has hard resource limits. When a quota runs out, checkouts return pointer files instead of data, and nothing warns you before it happens.

We cannot risk a contest stopping mid-flight because of a hard resource limit.

So the question in this deck is not whether to leave LFS, but how.

Start here. GitHub LFS bandwidth and storage are pooled per account and capped; once exhausted, LFS is blocked for the rest of the billing period and every checkout gets pointer text. On a contest day that is an outage with no warning. The rest of the deck is about replacing LFS for generated data.

THE PROBLEM

Large secret data in LFS costs bandwidth, breaks checkouts, and weakens tests

527 MB

of secret test data in LFS, 128 files in 41 draft problems. Every one was produced by a generator in the same problem.

3 PRs

in one day (#281–283): checkouts without LFS fed pointer text to input validators. Each fix moved data back into Git.

200k → 160k

nodes: one maximum case was cut to fit the 2 MiB limit. A weaker test, to avoid LFS.

The weekly verifyall sweep checks out with lfs: true, so every run downloads all of it. LFS quota is pooled per account: when it runs out, checkouts get pointers, which look like corrupted data.

The data is not precious: every LFS file in these problems was written by a generator that is committed beside it. We are paying storage and bandwidth for bytes we can recompute, and the workarounds (moving data back into Git, shrinking cases) cost test quality.

WHAT THE GENERATORS CAN ALREADY DO

39 of 41 generators rebuild their LFS data byte for byte

39

reproduce every LFS file exactly (sha256 equal to the pointer): 36 as committed, one only with GCC, one with its script’s own line for that case.

2

cannot: one generator crashes as committed; one no longer produces its committed data. 43 MB stays in LFS until fixed.

2

more defects found on the way: small committed cases that drifted from their generator, and a script naming a renamed file.

Checked without downloading LFS: an LFS pointer records the sha256 of its content, so regenerated bytes are compared with the pointer directly. Run: macOS, CPython 3.12, from a scratch copy of each package; GCC 15 where a generator needs <bits/stdc++.h>.

This is the key enabler. We do not need to trust that generators are deterministic: we measured it. And the same check found three real defects nobody had noticed, which is an argument for pinning regardless of which option is chosen.

SHARED BY BOTH OPTIONS

Each large file becomes one pinned line

data/secret/<case>.in
#ppf-stream regen secret/<case>.in
  sha256=f8bce43d…6d6d73 size=2577788

The generator is the source

generators/regen.sh runs the problem’s own command once, from a scratch copy of the package.

The pin is the guarantee

Bytes that don’t match sha256 and size are an error, never a silent change of test data.

Small cases stay as they are

Only the former LFS files change. A typical diff: 5 lines and a 6-line script.

The sha256 is taken from the LFS pointer, so converting needs no download. Because the pin is checked before anything uses the bytes, a generator that stops reproducing (new Python, new compiler) fails loudly instead of judging against different data.

OPTION 1 · PRE-CACHE AT BUILD TIME

Regenerate before anything reads the package

Repository

pins + generator; kilobytes

expand.py

run regen.sh once, check every pin, write the bytes

Ordinary package

the full data, as today

CI · contest system

verifyproblem, upload, judge: unchanged

Contestants and judges

See an ordinary batch problem. Nothing changes at contest time.

The cost

Someone, or something, must run expand before a package leaves the repository. Upload a raw checkout and the data is one-line pins.

Branches lfs/<problem>, plus ppf-stream-tools: one CI line runs expand.py before verifyproblem.

Option 1 keeps the contest exactly as it is. The data is generated once per build. The risk is procedural: a package exported without the expand step carries pins, not data, and an unprepared contest system would reject it at import, or, worse, judge against the pin text if no input validator runs.

OPTION 2 · ON THE FLY, INTERACTIVE IN NAME ONLY

The output validator generates, caches, and pipes the data

Judge

runs an interactive problem, as it already can

validate.py

first call: run regen once, check pins; later calls: cache

Submission

reads stdin as usual; end of input only if the harness delivers it

Default judge

the spec’s token compare, same flags

Contest systems

A conforming interactive package; input validators are wrapped to accept the pins. But see the end-of-input slide.

The cost

The first validation after the cache is cleared waits for generation, and contestants’ programs run under the interactive harness.

Branches lfs2/<problem>: problem.yaml gets validation: custom interactive; output_validators/ppf_stream carries the generator copy.

Option 2 changes nothing in contest systems: they already support interactive problems. A submission that reads its input and prints its answer works unchanged. What moves is time: the generator runs at judge time, once per cache. And the package duplicates the generator inside the output validator, because validators only see their own directory.

HAND EDITS · BOTH OPTIONS

gen → patch → pin: keep the edit, not the file

Generator

regen.sh, as committed

Patch

generators/patches/<case>.patch, a unified diff

Pin

sha256 of the edited bytes

Data

at build time (1) or judge time (2)

360 B

patch for five edits to a 2.6 MB case: a line added, one removed, the header and last line changed.

3.4×

what xz gives instead, over the 485 MB (gzip: 2.6×). Option 3, next, uses it where no generator exists.

0

silent changes: a patch that stops applying because the generator moved is an error with the line number.

mkpatch.py writes the patch from an edited file and re-pins the case. Works in both options; in option 2 the patch travels inside the validator’s copy of generators/.

Problem setters often touch up generated data by hand. Storing the edited file defeats the purpose; storing a patch keeps the repository small and makes the edit reviewable as a diff, which is what LFS made impossible. Compression is the other route: it works in both options too, but saves 3x, not thousands of times, and leaves binary blobs in history.

OPTION 3 · A TAR.XZ SHIM FOR A BROKEN OR MISSING GENERATOR

No working generator? A tar.xz stands in for it

Large cases

hand-made, or from a generator that crashes or drifted

archive.py

adds them to generators/data.tar.xz, pins each case

regen.sh

unpacks it, after the generator if there is one

Options 1 and 2

deploy it like any other problem

3.4×

what tar.xz saves (tar.zst 3.3×, zip 2.6×): 485 MB would be 142 MB. Pins save over 1000×.

2

problems use it today: problem A (17.8 → 7.3 MB) and problem B (24.9 → 4.3 MB).

6 s

to unpack every archive, against 174 s to regenerate. Byte-for-byte reproducible.

A shim, not a destination: it is real data in Git, re-committed on every change. Archives over 2 MiB are split into parts under the problem repository’s per-file limit, but the repository still holds them whole.

Option 3 answers “what if the generator is broken, or there never was one?” The data goes into a reproducible tar.xz under generators/, and its cases become pins like generated ones, so expansion, option 2, patches and the commit hook all work unchanged. It costs about a third of the data’s size in the repository, instead of almost nothing, and every change re-commits the archive. Retire it when the generator is fixed: put the generator back in regen.sh, delete the archive, and re-pin.

For option 1 the integration is one step in each system’s problem importer (PC², DOMjudge, Kattis): find directive files, run expand.py in a sandbox with the judge’s own limits, refuse the import if any pin fails. Until a system has that, CI can publish the expanded package as a build artifact to upload by hand. For option 2, each system already runs interactive problems, but problemtools’ harness, by design, keeps a submission’s input open until the validator exits, so programs that read to end of input hang; that harness behaviour must change (and DOMjudge’s and PC²’s checked), and the cache must be warmed on each judgehost before a contest. The generator’s toolchain (Python 3, C++ for some) is needed wherever generation runs.

Cold regeneration per problem, 39 problems. Median 1.3 s; 174 s for all; slowest 78 s. Warm cache: under 0.1 s.

Option 1: before the contest

Paid at build or import. Nobody waits on it during judging.

Option 2: at the first validation

The submission is already running, waiting on stdin, while the validator generates. A judge’s wall-clock limit can turn that wait into a false time-limit verdict.

So option 2 must be warmed

Run once to fill the cache before results count.

Measured on an Apple-silicon laptop, CPython 3.12, one problem at a time; judgehosts will differ, but the shape will not: most problems regenerate in about a second, a few take tens of seconds. The asymmetry is what matters. In option 1 the cost lands before the contest. In option 2 it lands inside the first judging run after a cache is cleared, while the submission’s wall clock is running.

OPTION 2’S HIDDEN COST · FOUND IN TESTING

Under problemtools, a submission never sees end of input

What happens

The interactive harness keeps the submission’s input open until the validator exits, by design. The validator cannot exit before the submission answers. A program that reads to end of input waits forever: a false time-limit verdict.

Who it hits

sys.stdin.read(), while (cin >> x), for line in sys.stdin. Among these problems’ own accepted solutions: 6 of 8 in Python, none of 44 in C++.

reads one line → accepted in 0.07 s
reads to EOF → killed at the 20 s wall limit

Same validator, same harness (problemtools/full, pinned by the repository’s CI). The fix is a harness change: deliver end of input when the validator closes its output. So option 2 is not change-free after all.

This was found running the repository’s own pinned verifier: the Python accepted solutions of one converted problem hung while its C++ ones passed. The harness source explains it: it deliberately keeps the write end of the validator-to-submission pipe open until the validator process exits, to make verdict races deterministic. Real interactive problems never wait for EOF, so this never mattered before. Kattis’s judge shares this lineage; DOMjudge and PC² should be checked.

A PROPOSAL, FOR THOSE WHO DECIDE

Option 2, with a run-twice policy for the first run of the week

Idle

Caches are dropped. A problem costs its pins and code: a fraction of its data.

First run of the week

Run twice. The first pass regenerates and checks every pin; its verdicts are not used. The second pass judges against a warm cache.

Before a contest

The same first pass on every judgehost, so no submission ever waits on generation.

Why: the space saving of option 2, without its first-run risk. Precondition: harnesses that deliver end of input, or option 1 for problems where solutions read to EOF.

Raised by the large-file-generator project as one option to weigh, not a decision. The choice belongs to the problem-repository maintainers and the contest-system teams.

This is the project lead’s suggestion, stated as a proposal. It combines option 2’s idle footprint with option 1’s property that nobody waits on generation during judging. The cost is one extra pass per week and one before each contest, about three minutes for these 39 problems on a laptop.

Both options rest on the same pins and the same generator, and the conversion tool can produce either from the same package, so the choice is reversible per problem. The difference is when generation happens and who has to remember to make it happen. Option 3 is not a third way to deploy: it replaces a broken or missing generator with an archive that regen.sh unpacks, and its cases are pins, so it ships as option 1 or 2 like any other problem.

FOR GENERATOR AUTHORS

Six habits that make any problem convert in one command

1 · One command, writes only data/

The common template (--mode all --root DIR) is why 30 problems converted with no per-problem work.

2 · Generate one case on request

--case secret/10_max to stdout bounds the first run to one case. None of the 41 can today.

3 · Prove it in CI

Pin by sha256 and regenerate on every change: the three drifted or broken generators would have failed at once.

4 · Determinism you can rely on

40 of 41 use randint, choice or shuffle, which Python does not promise to keep stable. Vendor a small RNG; seed per case.

5 · Portable builds, or none

Standard headers and c++, not <bits/stdc++.h> and g++; better, compute answers in the generator.

6 · Fast enough for judge time

Whole problem well under validation_time (60 s); the slowest here took 81 s.

Full text with the evidence for each point: docs/GENERATOR_ADVICE.md in the project’s private repository. The single most useful change is per-case generation, because it removes the first-run cost of option 2 and makes option 1 parallel.

WHAT CHANGED IN THE ADAPTER

From a pure streaming pattern to converting real packages

Mixed packages

Only pinned files are generated; every other case streams as committed. No per-case gen required.

Whole-problem regen

Runs the author’s own command once in a scratch copy, caches the tree, checks each pin.

Default judge

The spec’s default output validator as a program, with its flags: 40 of 41 problems need it.

Input guard

Existing input validators run unchanged on real data and accept the one-line pins.

expand.py

Option 1’s build step: restore every pin in place, or check only.

convert.py

LFS pointers to pins, LFS rules removed, either option, legacy packages.

The original appendix assumed a new problem written for streaming: one gen per case, one judge. Real problems have hand-made small cases, default validation, input validators and generate-everything scripts, so the adapter grew these six pieces. All are generic: no problem-specific code.
